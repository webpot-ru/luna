# YouTube Publication Campaigns

Source of truth для повторяемых смешанных волн публикации: несколько следующих ordinary-видео плюс Polyglot на каждый из 51 физического support-канала, без повторного выбора уже опубликованного контента и без независимой гонки календарей.

## Пользовательский контракт

Запрос вида «для Deck #2 опубликуй по 5 следующих ordinary и по 1 следующему full Polyglot на каждый канал» означает одну кампанию:

- support-слой: ровно 51 физический канал; `EN-GB -> EN`, `ES -> ES-419`, `PT -> PT-BR` как support/native, но региональные варианты сохраняются как target;
- ordinary: первые 5 незанятых tail assignment на каждый канал;
- Polyglot: первый незанятый full bundle tail на каждый канал;
- календарь: только shared allocator из `config/youtube-publish-schedule-policy.json`, самая ранняя безопасная свободная ячейка, без пропуска более ранней пустой даты;
- publication mode: `scheduled`, upload privacy `private`, публичность наступает в `publishAt`;
- runtime image generation: запрещена;
- `customThumbnailUploadAllowed=false` или неизвестное значение: видео разрешено, используется YouTube automatic thumbnail, custom cover не создается и `thumbnails.set` не вызывается;
- `customThumbnailUploadAllowed=true`: apply требует точный approved Git-tracked JPG с совпадающим checksum;
- `longVideoUploadAllowed` независим от custom-thumbnail capability. Только явное `true` разрешает full Polyglot дольше 15 минут; это не следует выводить из отсутствия/наличия JPG. Если значение `false` или неизвестно, planner до claim детерминированно меняет requested `full` на `short_unverified`, записывает `requestedContentScope=full` и `autoFallbackReason=long_video_upload_not_confirmed`, и ставит измеряемый потолок `895s` (`14:55`). Значение `shortUnverifiedPolyglotCardLimit=0` означает динамический максимум: renderer один раз измеряет cached TTS для candidate deck + intro/outro, берёт максимальный непрерывный префикс, который укладывается, и использует те же дорожки для render. Такой short не закрывает будущий full bundle tail; short/full pair for one support channel + bundle является hard preflight blocker. Старый/ручной claimed `full` на таком канале также блокируется dispatch preflight до metadata/TTS/render, а не после дорогой работы.
- Для каждого support planner выполняет no-spend `videoProductionReadiness` gate: проверяет tracked voice mapping и статус в `config/youtube-channels.json`. Edge voice с валидной map считается configured; другой provider требует явного `status=ready` и `checkedAt` после отдельной проверенной production-проверки. `status=blocked`/`unavailable` не делает общую волну ошибочной и не создаёт claim: подходящие строки поддержки записываются в `evidence.productionDeferredAssignments` как отдельный tail, без calendar slot, metadata, TTS или render. Exact partial recovery для заблокированной поддержки fail-closed и требует сначала восстановить readiness. Текущий `HY` имеет явный `status=ready`, reason `user_confirmed_ai33_generation`, `checkedAt=2026-07-26`; прежний smoke `30200194901` с transient `HTTP 503` не является ни подтверждением, ни запретом для этой отдельной user-confirmed readiness, а любая новая provider failure всё равно останавливает lane без retry.
- До metadata/TTS/render scheduled apply требует complete playlist discovery: уже существующий playlist обязан быть `public`, а complete no-match остаётся create-eligible (новый playlist создаётся public).
- никакого watch, автоматического retry или повторного dispatch.

Для полного стандартного запроса без production-deferred supports размер волны равен `51 * (5 + 1) = 306`: 255 ordinary и 51 Polyglot. Если readiness известной поддержки заблокирован, manifest явно показывает меньший фактический count и отдельный deferred tail; это не является молчаливой потерей строк. Целевая полная маршрутизация: `youtube-1=36`, `youtube-2=42`, `youtube-3=42`, `youtube-4=42`, `youtube-5=36`, `youtube-6=36`, `youtube-7=36`, `youtube-8=36`. Пока `publicationReady=false`, маршруты 5–8 добавляют явный blocker и не могут быть claimed/applied.

## Route subwaves

Начиная с 2026-07-31 пользовательское operational-правило для будущих публикаций: один стартовый route-subwave содержит не больше `5` физических support-каналов на каждый YouTube API project (`youtube-1`…`youtube-8`). Planner сначала формирует точную immutable кампанию из первых незанятых пяти supports каждого route; если на route осталось меньше пяти — включает только этот остаток. Следующий route-subwave создаётся только после итогового состояния первого, без замены или повторного выбора его claimed assignments.

Это одновременно лимит scope и фактический execution cap: parent campaign запускает до `40` workers (`5 × 8` routes), поэтому все пять выбранных физических каналов каждого проекта стартуют параллельно. Каждый support по-прежнему имеет собственный lock; меньшая доступная capacity GitHub может только поставить worker в очередь, но не меняет immutable manifest. Metadata по routes остаётся последовательной из-за общих provider secrets. Правило не меняет уже запущенные workflows и не разрешает новую публикацию, retry или обход quota.

## Почему старый bulk-контур давал дубли и пропуски

Старые ordinary и Polyglot dispatchers выбирали «следующие» элементы и писали календарь независимо в каждом child run. Между планированием и durable merge не было единой транзакции:

1. несколько workers могли прочитать одинаковое старое состояние;
2. каждый вычислял следующий target/slot самостоятельно;
3. видео могло успешно загрузиться, а child persist-job не успевал записать registry;
4. следующий запуск видел старый ledger и снова выбирал уже загруженное видео;
5. отдельные ordinary/Polyglot allocator passes могли занять календарь в разном порядке и оставить дату пустой;
6. 51 ordinary плюс 51 Polyglot worker делали около 102 мелких Gemini-запросов вместо крупных batch.
7. пустой `youtube_playlist_id` поздно трактовался как разрешение на `playlists.insert`, хотя это мог быть уже существующий, но не записанный локально плейлист.

Количество видео или строк registry никогда не является доказательством полноты. Apply разрешается только после authenticated eight-route live audit.

## Durable state

- `config/youtube-publication-snapshot.json`: свежий API readback, не apply token;
- `config/youtube-playlist-discovery-snapshot.json`: свежая полная route-authenticated инвентаризация owned playlists и их video IDs; не apply token;
- `config/youtube-publication-campaigns.json`: campaign state и receipts;
- `config/youtube-publication-campaign-plans/<campaignId>.json`: неизменяемый manifest;
- `config/youtube-publish-calendar.json`: shared physical-channel slots и campaign claims;
- `config/youtube-published-videos.json`: ordinary publications;
- `config/youtube-polyglot-published-videos.json`: Polyglot publications;
- `config/youtube-polyglot-progress.json`: Polyglot progress;
- `config/youtube-cover-assets.json`: approved cover manifests.

Campaign cover review для Deck #1 и Deck #2 строится детерминированно через `scripts/build-youtube-campaign-cover-review.mjs`: Deck #1 использует Git-tracked основу `assets/youtube-cover-templates/deck1-polyglot-approved-base.png`, Deck #2 — `assets/youtube-cover-templates/deck2-universal-approved-base.png`. Одобрение записывает exact campaign manifest в `config/youtube-cover-assets.json`, но apply остаётся заблокирован, пока manifest, JPG и sidecar не отслеживаются Git. Отсутствующие исторические manifest paths нельзя сохранять как active approved declarations: planner проверяет каждую такую запись fail-closed, даже если для assignment уже существует более новая точная обложка.

Campaign source deck тоже неизменяем: plan фиксирует SHA-256 локального Deck JSON. Apply допускает Git-tracked JSON, настроенный Drive file ID с той же локально проверенной копией либо подтвержденный исторический Git blob, чей object ID совпадает с локальным файлом. Read-only control preflight и apply сначала разрешают `data/deck-sources.json` и скачивают exact Drive JSON; только если Drive source отсутствует или не дал файл, они используют Git-tracked/historical fallback. GitHub runner делает full-history checkout, проверяет exact blob object, передаёт его parent metadata phase и обоим reusable workers, восстанавливает через `git cat-file blob` и затем сверяет фактический SHA. Commit-based `git show commit:path` остаётся legacy fallback; если commit указан вместе с blob, preflight требует точного `commit:path -> blobId` и блокирует mismatch. Deck #2 `home_kitchen_cooking_actions_a1_a2` сейчас подтвержден как historical blob `144f997ab79e4e99efaf18c0d7592fb904609dd1`; повторно коммитить игнорируемый 37 MB JSON не требуется.

Ordinary identity: `setId + canonical supportLang + targetLang`. Polyglot product identity: `setId + canonical supportLang + bundleKey`; `contentScope` и target hash являются атрибутами единственного продукта, не разрешением создать второй active video. Short не закрывает full tail, но active short/full pair в одном Polyglot product slot является blocker.

Legacy per-video planners may still emit a compatibility `polyglotKey` without the trailing `contentScope`. Campaign ownership detects product conflicts by the canonical unscoped `polyglotProductSlotKey` (`set + support + bundle`), while the scoped `polyglotSlotKey` remains the calendar-reservation identity. Exact ownership still requires the exact scope, canonical target set, campaign ID and manifest hash. A matching product with target or scope drift remains visible but does not satisfy campaign ownership.

Активная campaign claim блокирует повторный выбор assignment и физического `channelKey + publishAt` slot до `finalized` или отдельной подтвержденной reconciliation-процедуры.

## Integrated recovery wave

Если полная Deck #3 wave частично принята YouTube, а точные missing rows остаются в одном `claimed` campaign без receipt/artifact/YouTube ID, новая полная волна может включить их в свой лимит, но не может молча заменить их другими tail. `scripts/plan-youtube-integrated-recovery-wave.mjs` создаёт только no-spend manifest: фиксирует каждый source assignment, выбирает complement до строгих `ordinaryPerChannel + polyglotPerChannel` на каждом из 51 support-каналов и переносит source rows на будущие свободные slots. Scope Polyglot, включая `short_unverified`, сохраняется точно; source full/short нельзя подменять новым bundle.

Перед durable claim обязательны: свежий complete/healthy all-route control с pagination/status readback, отсутствие live collision для каждой конечной assignment identity, exact inclusion всех source keys, лимит каждого route `<=100` video inserts, aggregate limit и успешный dry-run `scripts/consolidate-youtube-unlaunched-claims.mjs`. Только затем этот consolidator атомарно помечает source claims/calendar reservations как `superseded_integrated_plan` и создаёт один новый claimed manifest. Planner, consolidator и этот переход делают `0` provider calls и `0` YouTube writes; parent apply остаётся отдельным явным действием.

Если fresh playlist discovery находит несколько public playlists с одной stable identity, выбор не делается по пустому ID или случайному порядку API. После явного пользовательского решения canonical ID сохраняется в `config/youtube-playlists.json`; discovery затем требует, чтобы именно этот ID принадлежал тому же channel. Для 13 исторических Deck #3 ordinary pairs `ET→KN`, `ET→LO`, `IS→KN`, `KA→HY/KK/KM/KN/LO`, `KK→HY`, `LO→KM`, `TL→HY/KK`, `UZ→HY` пользователь утвердил playlist с уже существующим видео Deck #2. Вторые legacy playlists не удаляются и видео между ними не перемещаются этой операцией.

## Safe publish sequence

1. Один read-only `.github/workflows/youtube-publication-control.yml`, без watch и без публикации. По умолчанию `audit_routes=ALL` сохраняет строгий аудит всех восьми active routes. Дополнительный opt-in режим принимает явный subset, например `audit_routes=youtube-6,youtube-7,youtube-8`; он разрешён только для campaign, чьи explicit `campaign_supports` целиком принадлежат выбранным routes. `ALL` в `campaign_supports` при route-scoped планировании запрещён. Для exact recovery допускается ещё более узкий read-only evidence mode: явные `audit_routes` вместе с `audit_supports=HY` читают только названный support в этих route и не могут использовать `audit_routes=ALL`, persist snapshot или строить новый campaign plan. Он доказывает только live state выбранного assignment scope и не заменяет normal all-route audit. Aggregate обязан доказать exact set выбранных route keys, а snapshot — наличие каждого выбранного support; отсутствие, лишний route или support вне scope блокируют plan. Полный свежий playlist-discovery snapshot может безопасно использоваться как superset для scoped campaign, если в нём есть каждый selected support, нет duplicate discovery и его complete/blocker/freshness gates проходят; planner использует только playlist rows selected support. Имена route artifacts принимаются в форме `youtube-N`, без жёсткого диапазона номеров; признак `all_routes` передаётся из selector workflow, а не выводится из случайного числа скачанных файлов. Этот вариант не заменяет и не ослабляет default all-route режим и не позволяет переносить канал на чужой OAuth/API project. Без campaign-плана workflow читает uploads pagination и `videos.list(status)` для выбранных routes, строит свежий live snapshot и не обходит плейлисты. Для no-spend campaign-плана передать точные `campaign_supports`, `campaign_ordinary_per_channel` и `campaign_polyglot_per_channel`: workflow дополнительно читает только owned playlists этих support-каналов. State drift сохраняется как evidence/snapshot with blockers instead of aborting audit job; campaign planning/apply remains blocked until selected-scope duplicates, registry and calendar blockers are zero. Live snapshot и выбранный playlist-discovery snapshot должны быть не старше 30 минут.

Финальная ordinary-волна исчерпываемой колоды может явно передать `campaign_allow_partial_ordinary_tail=true`. Этот режим сохраняет `campaign_ordinary_per_channel` как верхнюю границу, но допускает меньше назначений только там, где после исключения live publications и active claims больше нет unclaimed ordinary tails. Без явного флага exact-count gate остаётся строгим. Режим не разрешает дубли, замену set ID или автоматическое дополнение из следующей колоды.
2. Локальный planner ниже остается эквивалентным fallback для уже скачанных exact snapshots; не запускать второй независимый selector поверх GitHub plan:

```bash
npm run plan:youtube-publication-campaign -- \
  --set=home_kitchen_cooking_actions_a1_a2 \
  --supports=ALL \
  --ordinary-per-channel=5 \
  --polyglot-per-channel=1 \
  --min-future-minutes=90 \
  --max-snapshot-age-minutes=30 \
  --require-apply-ready \
  --output=outputs/youtube-publication-campaign-plan.json
```

3. Показать exact assignments, явный список `productionDeferredAssignments`, schedule range, route counts, cover readiness, playlist readiness и cost/quota estimate. Для каждого assignment playlist может быть только `resolved_existing` с проверенным live ID либо `verified_absent` после полной channel inventory. Blank registry ID без discovery остается blocker. Остановиться до explicit approval.

Quota estimate разделяет `estimatedVideoUploadCalls` и general quota, включая `byRoute`. Для general quota план показывает `playlistItems.insert=50` на видео, `playlists.insert=50` только для `verified_absent`, и `thumbnails.set=50` только для разрешённой custom cover. Пока playlist discovery отсутствует, cost preflight fail-closed считает maximum create для всех assignments. Историческая оценка `100 units` за `videos.insert` здесь не используется. Стандартные route shards `36/42/42/42/36/36/36/36` остаются ниже 100 upload calls на route; вся кампания обязана укладываться в единый предел 800 upload calls per America/Los_Angeles quota day. Standby route не используется для обхода этого предела.

4. После approval записать одну атомарную claim и immutable manifest:

```bash
npm run claim:youtube-publication-campaign -- \
  --manifest=outputs/youtube-publication-campaign-plan.json \
  --apply \
  --confirm=CLAIM_YOUTUBE_PUBLICATION_CAMPAIGN
```

5. Commit/push только exact code/config/manifest/assets по проектным Git-правилам. Apply из незапушенной ветки запрещен.
6. Один fire-and-forget `.github/workflows/youtube-publication-campaign.yml` в `mode=apply` с exact `campaign_id`, `campaign_manifest_hash` и `confirm_campaign_apply=APPLY_YOUTUBE_PUBLICATION_CAMPAIGN`. Apply preflight заново сверяет channel production readiness и запрещает legacy `full` Polyglot без `longVideoUploadAllowed=true` до metadata/TTS/render. Затем он строит worker matrix только для video type, который запрошен в claimed campaign: ordinary-only и Polyglot-only recovery campaigns валидны; отсутствующий другой type не является blocker. Empty reusable matrix GitHub может отдать как `skipped` или `failure`, поэтому Polyglot worker опирается на точный preflight `ordinary_worker_count`: ноль разрешает следующий worker, любое требуемое ordinary failure блокирует его. Finalizer считает non-success допустимым только для типа с нулевым expected count. Parent передаёт reusable ordinary/Polyglot workers внутренний boolean `campaign_owned_apply=true`, объявленный только в `workflow_call`; ручная `workflow_dispatch` форма его не экспонирует. Защита не использует `github.event_name`, потому что reusable worker наследует событие parent. Каждый worker строит strict authenticated report до render и ещё раз непосредственно перед upload: ordinary report scoped to `ordinary` и привязан к exact worker targets, Polyglot report scoped to `polyglot` и привязан к exact bundle candidate. Scope исключает только ожидаемый другой video type из live/registry completeness текущего worker; общие calendar collisions и свежие unclassified uploads остаются блокерами. Uploader сверяет, что report разрешает именно тип загружаемого metadata.
7. Не смотреть child runs непрерывно. Один bounded readback позже. На failure после metadata/render/TTS/image остановиться и сообщить artifact/stage; не retry и не reupload.

Для exact partial recovery route report может содержать уже известные blockers других support-каналов, если эти blockers появились после parent upload и не относятся к выбранному recovery. Такой recovery допускается только когда complete/status/pagination evidence остаётся свежим, у выбранных support-каналов и у global-слоя blockers ровно ноль, а validator явно сохраняет число проигнорированных unrelated blockers. Он не разрешает обходить blocker выбранного канала, global blocker, duplicate или product-slot collision.

`youtube-video-publish.yml` и `youtube-polyglot-video-publish.yml` являются только внутренними reusable workers: их ручной `workflow_dispatch mode=apply` намеренно запрещён. Это исключает независимые calendar claims, per-child live control и competing state commits; новые волны запускаются только через уже claimed campaign.

## Точный repair scheduled даты

`youtube-repair-scheduled-publish-at.yml` обслуживает только committed plan `config/youtube-schedule-repair-plans/deck1-polyglot-calendar-conflicts-20260715.json`. Он не создаёт новую публикацию: перед единственным `videos.update(status)` сверяет владельца канала, `private` и прежний `publishAt`. После write workflow делает bounded propagation readback: ждёт 15 секунд, затем читает тот же ID максимум три раза с двумя дополнительными паузами по 10 секунд. Он никогда не повторяет `videos.update`; в failure evidence сохраняет `before`, ответ update и все post-update readback. В workflow нет render, TTS, metadata, thumbnails, playlist operations, uploads или deletes. Если первый ID даёт mismatch или API error, второй не пытается менять. Уже перенесённый на точную целевую дату ID остаётся read-only.

## Metadata batching

Campaign apply сначала выполняет отдельную metadata matrix по всем `publicationReady=true` routes. Route jobs стоят в очереди с `max-parallel: 1`, потому что используют общие provider secrets; GitHub runner queue сама по себе не считается ограничителем provider concurrency. Внутри route ordinary и Polyglot tasks смешиваются в synchronous batches до 5 независимых `requestId` на один запрос. После GitHub activation всех восьми маршрутов стандартная волна 306 видео потребует 67 route-batched requests (`8 + 9 + 9 + 9 + 8 + 8 + 8 + 8`), а не 102 child-worker requests. Теоретический global minimum равен 62, но route split сохраняется, потому что route artifacts/checkpoints и GitHub Environments разделены. Batch size `5` является production maximum: run `29323860280` доказал, что batch `10` может трижды превысить output capacity (`MAX_TOKENS` на обоих direct keys, затем truncated VectorEngine JSON) до render/TTS/upload.

После metadata parent workflow ограничивает ordinary и Polyglot matrices `max-parallel: 40`: это до пяти top-level apply workers на каждый из восьми маршрутов первой route-subwave. Пока 5–8 blocked, кампания с ними останавливается в preflight; она не заменяет их тихо маршрутами 1–4. Per-channel lock в reusable workflow защищает только один channel, а не общий route/project quota. Внутри worker остаётся `concurrency=2`; запуск шестого канала того же проекта не разрешён, пока не будет durably завершена/сверена предыдущая пятёрка.

Production chain после отдельного `confirm_openai_metadata=USE_OPENAI_METADATA` состоит только из OpenAI Responses API: `gpt-5.6-terra` как основная модель и `gpt-5.6-luna` как резерв. Direct Gemini и VectorEngine намеренно отключены для campaign metadata; непустой `confirm_vectorengine_metadata` fail-closed останавливает run до provider call. Основная OpenAI-модель зафиксирована в workflow как `gpt-5.6-terra`; GitHub variable не может переопределить её на flagship-модель. `gpt-5.6-luna` используется для кампании от `100` assignments либо для следующих batches, если успешный Terra batch превысил `6000` input+output tokens на assignment. Обе модели используют Structured Outputs, `store=false`, explicit low reasoning/verbosity, до `5` задач и `max_output_tokens=12000`. `OPENAI_SERVICE_TIER` принимает только `auto`, `default` или `flex`; production default — `auto`. Чужой, отсутствующий или дублированный `requestId`, incomplete/refused response и invalid JSON являются recoverable response-integrity failure конкретного backend: такой ответ не принимается и metadata chain переходит к Luna; после Luna run останавливается без стороннего AI fallback.

Операционный ориентир расхода — около `2,000,000` OpenAI input+output tokens на стандартную восьмимаршрутную кампанию. Parent пропорционально распределяет единый campaign budget между route jobs по числу assignments; сумма всех route budgets всегда равна `2,000,000`, а не `500,000 * 8`. Перед каждым request generator резервирует консервативный верхний предел `UTF-8 bytes полного structured request + max_output_tokens`; если следующий request превысит route budget, OpenAI не вызывается и route fail-closed останавливается без Gemini/VectorEngine fallback. Exact actual input/output usage сохраняется в route checkpoint. Это приблизительный campaign guard, а не organization-wide daily hard cap: несколько отдельных campaign runs и другие приложения с тем же key учитываются независимо.

Если OpenAI и оба direct Google key не дали полный валидный ответ, только VectorEngine fallback делит этот логический batch на подбатчи максимум по `2` (`2+2+1` для пяти задач). Каждый подбатч отдельно обязан вернуть complete JSON с exact request-id set; затем результаты объединяются в исходном порядке и повторно валидируются целиком. Для `gemini-3.5-flash` каждый provider request передает `maxOutputTokens=60000` при модельном output limit `65536`; prompt ограничивает description 3-5 короткими предложениями / 900 Unicode characters и Polyglot playlist description 600 characters. Length gates count Unicode code points with `Array.from`; `ZH`, `JA` and `KO` require at least `150`, not the Latin-script minimum. Exact request-id set и language/SEO gates обязательны. Если metadata phase падает, TTS, render и YouTube upload jobs не стартуют.

OpenAI Batch API не используется в этом synchronous campaign workflow: он даёт 50% price reduction, но имеет completion window до 24 часов и требует upload JSONL -> create batch -> bounded completion readback -> output merge. Без отдельного двухфазного planner он может оставить уже claimed календарные слоты без готовых metadata. Flex можно включить через `OPENAI_SERVICE_TIER=flex`, но он предназначен для менее срочных задач и может быть медленнее/временно недоступен; при действующей бесплатной data-sharing квоте преимущество Flex не доказано, поэтому default остаётся `auto`.

Metadata generator пишет атомарный `index.json` checkpoint до provider call и после каждого полностью завершенного batch. Metadata artifact загружается с `if: always()` даже при последующем падении route. Автоматического retry нет. Только отдельно подтвержденный recovery dispatch может передать `metadata_resume_run_id=<prior-run-id>`: workflow скачивает exact route artifact, а generator повторно использует лишь batch, у которого совпадают campaign id, manifest hash, route, batch size, assignment count, destination, artifact SHA-256 и metadata ownership. Отсутствующий artifact означает обычную генерацию в рамках подтвержденного recovery; несовместимый, поврежденный или частичный checkpoint блокирует provider calls. Для отмененного или упавшего metadata-only run без render/TTS/YouTube write допускается один явно подтвержденный recovery той же immutable campaign без нового all-route audit: только с теми же ID/hash и compatible checkpoint, после исправления точной причины сбоя. Это не разрешение повторно запускать campaign без safe publish protocol.

## One finalizer

Campaign child workflows получают `campaign_id`, поэтому их standalone persist jobs автоматически отключены. Campaign-поля доступны только через внутренний `workflow_call` и не занимают ограниченный 25 inputs ручной формы. После всех workers один parent finalizer последовательно объединяет artifacts, сопоставляет publications с `campaignId + manifestHash`, обновляет registry/calendar/receipts и делает один exact state commit.

Отключать `--strict` для campaign-owned worker запрещено. Исторический обход скрывал расхождение контракта: checker записывал `evidence.strict=false`, а uploader всё равно требовал `strict=true`, поэтому будущий campaign upload мог дойти до uploader только чтобы остановиться до `videos.insert`. Type-scoped strict control устраняет ложный cross-type drift внутри одной незавершённой кампании без ослабления duplicate, status, registry, unclassified-upload и shared-calendar gates.

Перед `playlists.insert` campaign uploader повторно перечисляет все owned playlists и ищет stable key marker или exact deterministic title. Найденный один playlist используется без создания; несколько совпадений блокируют write; только complete no-match разрешает один create. Новый playlist получает marker `LunaCards playlist key: <stable-key>` в description.

Если historical playlist duplicates уже существуют, их не удаляют и не меняют в ходе publication recovery. Сначала фиксируют один durable `youtube_playlist_id` только при доказуемом live readback: тот же channel, complete playlist-items pagination и membership актуального published video для данной stable identity. В registry сохраняют ID, timestamp и evidence; после этого fresh control может использовать ID как authoritative. Совпадение только по title/description или наличие старого Deck #1 video недостаточно.

Если duplicate playlist блокирует только выбранный ordinary target, planner может явно передать `--exclude-ordinary-targets=<codes>` и выбрать следующий unclaimed ordinary tail. Исключение записывается в immutable manifest, действует для всех support channels этой волны и не удаляет, не объединяет и не переиспользует ambiguous playlist. Оно не ослабляет strict `ordinaryPerChannel` и не разрешает обходить blocker для уже выбранной пары.

`finalized` допустим только когда присутствуют все expected receipts, один YouTube ID не назначен двум assignments, `publishAt` совпадает с claimed slot, обязательная custom cover реально установлена, есть `youtubePlaylistId` и `playlistItemId`, resolved playlist ID совпадает с manifest и нет `postUploadError`. Любая неполнота или mismatch дает `reconciliation_required`; claims сохраняются, а автоматический повтор запрещен. Сначала нужен новый read-only live audit и exact reconciliation plan.

### Post-upload schedule reconciliation

Если все expected upload receipts уже существуют, а единственной причиной `reconciliation_required` являются сдвинутые фактические `publishAt`, допустима отдельная локальная финализация через `npm run reconcile:youtube-campaign-schedule`. Она всегда начинается с dry-run и требует complete all-route control report с полной pagination/status readback вместе с publication snapshot из того же audit artifact. Допускаются только точные blockers `live_schedule_missing_calendar` для тех же campaign video IDs; каждый такой ID обязан быть private scheduled в snapshot, совпадать по полной assignment identity с durable receipt и не иметь конфликта в фактическом `channelKey + publishAt` slot. Для legacy Polyglot snapshot без `targetLangsHash` или `polyglotKey` полная identity доказывается теми же canonical `setId`, support language, `bundleKey`, `contentScope` и order-independent canonical target set; отсутствие хеша само по себе не ослабляет проверку. Missing receipts, duplicate/unexpected publications, другие blockers, playlist/thumbnail/post-upload errors или public/unknown live state блокируют операцию.

`--apply --confirm=RECONCILE_YOUTUBE_CAMPAIGN_SCHEDULE` меняет только local durable state: calendar получает фактический live `publishAt` и `campaign_finalized`, campaign receipt получает `actualPublishAt` и evidence path, top-level campaign становится `finalized`. Для durable evidence передают `--report-evidence=<GitHub run URL или tracked path>`: локальный путь `--report` служит только для чтения и не становится частью durable state. Immutable manifest, его SHA и исходные claimed slots не переписываются. Команда не вызывает provider, render, TTS, GitHub workflow или YouTube API и не переносит публикацию на YouTube.

## Zero-upload re-arm

Если finalizer доказал `completedCount=0`, `observedCount=0`, `artifactCount=0`, а два complete all-route control reports до и после failure имеют идентичный YouTube video-ID set, допускается отдельный zero-upload re-arm. Planner получает `--replacement-campaign-id=<old-id>` и виртуально исключает только эту `reconciliation_required` campaign из assignment/slot claims; исходные registry/calendar остаются неизменными до apply. Новый manifest обязан содержать ровно тот же assignment-key set, новый campaign ID/hash и безопасные будущие слоты.

`npm run rearm:youtube-publication-campaign` по умолчанию является dry-run. Apply требует `--confirm=REARM_ZERO_UPLOAD_YOUTUBE_PUBLICATION_CAMPAIGN`; он fail-closed проверяет оба control reports, exact live-ID equality, zero campaign receipts/artifacts, exact assignment identity, old claim integrity, other-campaign conflicts, slot collisions, canonical identities и минимальный future buffer. Только после этого старые campaign/calendar rows становятся `superseded_zero_upload_recovery`, а новый immutable manifest и claims записываются вместе. Это локальная durable-state операция: provider calls и YouTube writes равны нулю, publication dispatch остаётся отдельным подтверждением.

Если exact before/after control reports уже доказывают zero-upload и равенство live-ID set, replacement planner может читать только snapshot и playlist-discovery artifact из этого after report с ограниченным evidence window. Это разрешено исключительно при `--replacement-campaign-id` перед немедленным `rearm`; manifest обязан сохранить exact assignment set, а `rearm` повторно валидирует оба reports. Такой artifact не является свежим общим разрешением на обычный publish plan и не отменяет строгий pre-upload readback.

## Unlaunched claimed-campaign rollover

Если immutable campaign была `claimed`, но parent workflow ни разу не dispatch-ился и её слоты успели устареть, запрещено запускать её с прошедшими датами или вручную менять статус/календарь. `npm run rollover:youtube-claimed-campaign` создаёт новый immutable manifest с тем же exact assignment-key set и безопасными будущими слотами. Старые campaign/calendar claims становятся `superseded_unlaunched_claim_rollover`; новая campaign получает собственные ID/hash и `rolloverOfCampaignId`.

Rollover является fail-closed локальной durable-state операцией. Он требует source status `claimed`, отсутствие campaign/assignment/calendar dispatch, finalizer, artifact и YouTube receipt evidence, exact integrity старого manifest и claims, отсутствие конфликтов с другими active campaigns, а также свежий complete control report с полной pagination/status readback, без recent unclassified uploads, selected blockers и live video IDs для переносимых assignments. Dry-run является default; apply требует `--confirm=ROLLOVER_UNLAUNCHED_CLAIMED_YOUTUBE_CAMPAIGN`. Provider calls и YouTube writes равны нулю. Commit/push нового manifest/registry/calendar и последующий publication dispatch остаются отдельными действиями.

## Integrated unlaunched-claim consolidation

Когда несколько активных `claimed` хвостов одной колоды нужно безопасно собрать в единую строгую волну, применяется `scripts/consolidate-youtube-unlaunched-claims.mjs`. Это не retry, не reconciliation accepted uploads и не изменение immutable source manifests: новый manifest получает собственные ID/hash и только заранее подготовленные назначения. Default — dry-run; локальный apply требует `--confirm=CONSOLIDATE_UNLAUNCHED_YOUTUBE_CLAIMS`.

Операция fail-closed требует complete/healthy all-route control report не старше заданного окна, полной pagination и `videos.list(status)` readback, `0` selected blockers/duplicates/calendar collisions/recent unclassified uploads, а также exact one-to-one source assignment ↔ active calendar reservation. Каждый переносимый source row обязан быть `claimed`, без YouTube ID/URL, upload receipt, artifact, playlist item или finalizer evidence; полный live assignment/product-slot check и проверка будущих slot collisions повторяются для нового manifest. Он обязан быть apply-ready, block-free и иметь строгий объявленный размер support × (ordinary + Polyglot).

При apply source assignment и calendar reservation получают `superseded_integrated_plan`, ссылку на новый campaign ID и причину; top-level campaign становится `superseded_unlaunched_claim_consolidation` только если в ней не осталось иных active rows. Эти статусы освобождают лишь точные перенесённые assignment/slot/product claims, не меняют accepted receipts и сохраняют исторические manifests как evidence. Команда не вызывает provider, render, TTS, GitHub workflow или YouTube API; commit/merge и последующий parent apply остаются отдельными подтверждаемыми действиями.

Standalone ordinary/Polyglot workflows сохраняют собственный persist-job для одиночных legacy-запусков. Они не являются основным путем для смешанной 51-channel campaign. Parent campaign preflight выводит отдельные worker counts; если ordinary или Polyglot matrix пуста, соответствующий job пропускается до GitHub matrix evaluation. Это сохраняет valid ordinary-only и Polyglot-only campaigns без ложного workflow failure.

## Partial recovery after accepted uploads

### AI33 interrupted-render recovery

Временный `429`/`5xx`/network error при опросе статуса AI33 не является доказательством потери задачи. Для HY renderer делает bounded retry status-readback (по умолчанию шесть попыток с exponential backoff) и сохраняет до первого poll non-secret JSONL ledger `outputs/video-generator/cache/*/ai33-task-ledger.jsonl`: exact task ID, hash-addressed cache filename, voice ID и хеш текста. В ledger не записываются исходный текст, ключи или временный `audio_url`. При перезапуске exact cache file сначала возобновляет этот task ID, а не создаёт новый TTS task; server-side failed/cancelled task и исчерпанный polling остаются fail-closed.

Campaign apply может принять `video_cache_resume_run_id` только вместе с `video_cache_resume_support`. Перед копированием из failed child artifact workflow сравнивает `setId`, support и shard targets старого `youtube-generation-targets-github.json`: текущий worker обязан быть тем же exact set/support и содержать только targets, уже входившие в source worker. Это безопасно для hash-addressed audio cache: несовпадающий текст или voice ID всё равно даёт cache miss. MP4, metadata, calendar, receipts и YouTube state из source artifact не переиспользуются. Отдельный publication control/preflight и явное apply-подтверждение остаются обязательными.

Для `playlists.insert` и `playlistItems.insert` campaign apply не отключает API retry. Особенно для `playlistItems.insert` каждый transient failure сначала получает fresh paginated readback exact `playlistId + videoId`: уже вставленный item принимается как idempotent success, а подтверждённо отсутствующий item повторяется bounded backoff. Только после исчерпания retry запись становится `needsPlaylistInsert`; это исключает повторную загрузку видео при временном ответе YouTube `409 SERVICE_UNAVAILABLE` / `ABORTED`.

An active `short_unverified` Polyglot keeps the corresponding future `full` tail open, but that deferred tail is an advisory rather than a global control blocker. The same product slot still fails closed if a campaign actually proposes the full assignment while the short remains active, and simultaneous active short/full publications remain duplicate cross-scope blockers. Upgrading therefore still requires an exact replacement decision; unrelated ordinary or next-bundle campaign work is not blocked merely because the future full upgrade is not yet possible.

Если finalizer уже зафиксировал часть YouTube IDs, zero-upload re-arm запрещён. Точный partial recovery использует `npm run recover-partial:youtube-publication-campaign`: только выбранные отсутствующие assignments без YouTube ID получают статус `superseded_partial_recovery`, их старые календарные claims освобождаются, а остальные completed/missing строки исходной campaign не меняются. Новый immutable manifest строится только из свежих здоровых route-control reports и повторно назначает следующие свободные shared-calendar slots. Если исходная campaign была создана до пересмотра active route assignment, explicit recovery заново разрешает для каждого support текущие canonical `routeKey` и GitHub environment, сохраняет source route в evidence и никогда не использует устаревший OAuth bundle; это не является automatic quota failover. Polyglot сохраняет исходный scope, если это `short_unverified` либо если `full` имеет `longVideoUploadAllowed=true`; иначе selected unaccepted `full` автоматически становится measured `short_unverified` и записывает fallback reason до claim. Явный `--polyglot-scope-downgrades-file` по-прежнему допускает только `full -> short_unverified` для выбранного исходного `claimed` full assignment без YouTube ID/URL и после fresh control без live video в том же product slot. Это обычный видеоурок `<=895s`, а не вертикальный YouTube Short; он не закрывает будущий full tail. Blocked `videoProductionReadiness` никогда не получает recovery claim и остаётся отдельным tail до восстановления provider readiness. Для ordinary partial recovery число строк может различаться между support-языками: новые manifest обязаны зафиксировать `allowPartialOrdinaryTail=true`, а dispatch preflight принимает от `1` до максимума `ordinaryPerChannel` для каждого выбранного support. Ранее созданные immutable manifest с `partialRecoveryOfCampaignId` получают ту же обработку для обратной совместимости. После exact commit/merge запускается одна новая campaign; direct child dispatch и полный повтор исходной campaign запрещены.

Для смешанного хвоста exact selection задаётся через `--assignment-keys-file`: каждый ключ должен существовать в исходной campaign, оставаться без принятого YouTube ID/receipt/upload artifact и пройти текущую live collision-проверку по полной assignment identity. Ordinary и Polyglot разрешены в одном recovery manifest, но preflight проверяет их матрицы отдельно через `ordinarySupportCount` и `polyglotSupportCount`; общий `supportCount` сохраняется только как legacy fallback. Polyglot сохраняет исходный bundle; full сохраняет scope только при подтверждённом long-video capability, иначе recovery до claim создаёт short fallback. Ordinary сохраняет точный target-язык. Параметр `--generated-at` фиксирует время построения, поэтому dry-run и apply при неизменных inputs дают один campaign ID/hash. Уже принятые assignments, несопоставимые live uploads и посторонние claims остаются fail-closed blockers.

Текущий tail selector может не вернуть exact source key, пока этот же key ещё удерживается исходной `reconciliation_required` campaign. Такое отсутствие в `tails` не является blocker для partial recovery: immutable source identity и complete fresh live collision check остаются обязательными, а повторный selector не вправе заменить source assignment на следующий bundle/target.

Явно подтверждённая замена пустого `short_unverified` claim на full оформляется только через exact partial recovery с `--polyglot-scope-upgrades-file`: ключом служит исходный `assignmentKey`, значением — только `full`. Recovery принимает исключительно выбранный short без YouTube ID/receipt/artifact, требует свежий control report без live-видео в том же Polyglot product slot и `longVideoUploadAllowed=true`; создаётся новый full claim. Источник может быть `reconciliation_required` либо строго unlaunched `claimed` без dispatch/finalizer evidence и без принятого source assignment. Нельзя менять scope у full, у невыбранной строки или у уже принятой публикации; автоматического upgrade не существует.

Claim selection обязан читать статус каждой подробной campaign assignment. Строка `superseded_partial_recovery` больше не принадлежит исходной campaign и не может повторно блокироваться её stale top-level `assignmentKeys` или `slotKeys`; claim переносится на exact recovery campaign. Верхнеуровневые массивы остаются fail-closed fallback только для legacy campaign без соответствующей подробной строки. Все остальные статусы активной campaign продолжают блокировать assignment, календарный slot и Polyglot product slot до live reconciliation/finalization.

Для обычной campaign с `allowPartialOrdinaryTail=true` общий `supportCount` описывает audited/selected support scope, а worker matrix содержит только supports с фактическими ordinary assignments. Если immutable manifest не содержит отдельный `ordinarySupportCount`, dispatch preflight выводит его из canonical ordinary assignments и по-прежнему требует от `1` до `ordinaryPerChannel` строк на каждый такой support. Пустые workers для supports без ordinary-хвоста не создаются; в строгом режиме без partial flag matrix обязана совпадать с общим support count.

Параметр `polyglotPerChannel=N` является строгим равномерным контрактом: выбран каждый support и каждый из них обязан дать ровно `N` доступных Polyglot tails. Он не означает «до N» и не подходит для позднего неравномерного хвоста по всем `51` каналам. Такой хвост разбивается на отдельные no-spend планы по supports с одинаковым доступным количеством либо на exact-key recovery, когда assignment уже принадлежит незавершённой campaign. Нельзя ослаблять строгий счётчик только ради получения большого mixed batch.

Если scheduled recovery блокируется существующим `unlisted` playlist, `.github/workflows/youtube-video-visibility.yml` запускается с `playlist_only=true`, пустым `video_id` и exact `playlist_id`. Этот режим проверяет OAuth channel ownership, меняет и читает обратно только playlist; использовать произвольное существующее video ID как технический носитель запрещено. Операция идемпотентна: уже совпадающая visibility не вызывает повторный PUT, а после изменения workflow делает bounded delayed readback, потому что немедленный `playlists.list` может кратковременно вернуть предыдущее состояние.
